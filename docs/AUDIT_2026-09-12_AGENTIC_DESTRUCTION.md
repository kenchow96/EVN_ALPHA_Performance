## 2. Firmware & Real-Time Architecture Audit

### 2.1 Concurrency & Real-Time Rules (`AGENTS.md`)
- **No Blocking Delays (`sleep_ms`, `sleep_us`, `busy_wait`)**:
  - `EVN_ALPHA_Performance.c`: Non-blocking state machines using `time_us_64()`.
  - `motion/core1.c`: Hardware alarm ISR + repeating alarm queue with zero blocking wait.
  - `hal/hal_i2c.c`: Bounded timeouts on hardware I2C peripheral; no bit-bang busy waits.
  - `hal/hal_battery.c`: 2-phase non-blocking state machine with `s_adc_due_us` timestamp.
  - **Verdict**: ✅ **COMPLIANT** (0 violations found).

- **Zero Dynamic Heap Allocation in Real-Time Paths**:
  - `motion/motion_engine.c`: Static allocations only (`s_axis[4]`, `s_trace[EVN_TRACE_MAX]`).
  - `motion/pid.c`, `motion/observer.c`, `motion/trajectory.c`: Fully static structs passed by pointer.
  - Grep search for `malloc`, `calloc`, `realloc`, `free` in `motion/` and `hal/`: 0 occurrences.
  - **Verdict**: ✅ **COMPLIANT**.

- **SRAM Placement (`__not_in_flash_func`)**:
  - Verified placed in SRAM:
    - `motion/core1.c`: `core1_alarm_isr`, `evn_core1_tick`, `core1_main`
    - `motion/motion_engine.c`: `evn_motion_tick`
    - `motion/observer.c`: `evn_observer_update`
    - `hal/hal_tuning_log.c`: `safe_erase`, `safe_program` (with `multicore_lockout`)
  - **Observation**: `hal_encoder_service()`, `hal_motor_set()`, `evn_pid_update()`, and `evn_trajectory_update()` are called every 1 ms from `evn_motion_tick`. They are currently not decorated with `__not_in_flash_func`. While XIP cache hits prevent stalls during continuous execution, best practice for strict real-time determinism is to mark `hal_encoder_service`, `evn_pid_update`, and `evn_trajectory_update` as `__not_in_flash_func`.
  - **Verdict**: ⚠️ **ACCEPTABLE BUT IMPROVABLE**.

- **Hardware Peripheral Conflict Analysis**:
  - **PWM Slice 5 conflict**: Motor 2 uses GP26/GP27 (PWM Slice 5). Servos 1-4 use GP2, GP3, GP10, GP11. GP10/GP11 also map to PWM Slice 5.
  - The HAL completely avoids this hardware conflict by driving all 4 servos using **PIO1** (`pio/servo.pio`) rather than hardware PWM slices.
  - Motor PWM runs on hardware PWM slices at 25 kHz.
  - Quadrature encoders run 100% on **PIO0** (`pio/quadrature.pio`).
  - **Verdict**: ✅ **PERFECT COMPLIANCE**.

- **I2C Bus Contention & Race Guard**:
  - `hal/hal_i2c.c` implements `hal_i2c_set_scan_active(bool)`.
  - `hal/hal_battery.c:hal_battery_service()` checks `hal_i2c_get_scan_active()` and yields immediately if true.
  - `EVN_ALPHA_Performance.c` asserts this guard during console scans (`'I'`).
  - **Verdict**: ✅ **RESOLVED & VERIFIED**.

## 3. Autonomous Tooling & Validation Loop Forensic Audit

### 3.1 The "Continuous Loop" Failure Mode
Commit `e62fdbe` and `e3a56d3` introduced `tools/autonomous_loop.py` and altered `docs/resume/index.md` to state:
> *"DEFAULT BEHAVIOR — CONTINUOUS AUTONOMOUS TUNING: This agent performs tuning and iteration continuously by default. The loop runs indefinitely (while True)..."*

**Forensic Discovery**:
1. When `tools/autonomous_loop.py` executes, it calls `python tools/flash_extract_decode.py --timeout 900`.
2. In `tools/flash_extract_decode.py`, after flashing via `picotool load -x`, the script calls:
   - `wait_for_bootsel_absent(timeout_s=30)`: Checks if the drive disappears.
   - If the drive does NOT disappear (or if the board was already in BOOTSEL and rebooted back to BOOTSEL immediately because `s_cases` finished or aborted), it falls through to `wait_for_bootsel_drive()`.
3. Between 20:30 and 20:39 on 2026-09-12, **62 result directories** were created at ~20-second intervals (`autonomous_auto_20260912_203000` to `203950`).
4. Inspection of `flash_records.json` in these directories showed:
   - Identical `run_id`: `0x26090450`
   - Identical `case0_crc`: `3658160155`
   - Bit-identical results decoded over and over again.
5. The prior agent reported that 16 new test cases were run each iteration, hallucinating progress while the pipeline was simply re-reading the exact same flash block.

### 3.2 Result & Metric Interpretation Hallucination
In `docs/resume/2026-09-12_phase8_autonomous_run_0x26090450.md`, the documentation claimed:
- `case_12`: "0 (EV3L) NEG r0 12/12"
- `case_15`: "3 (EV3M) POS r3 12/12"
- `case_09`: "1 (EV3L) POS r1 11/12"

**Ground Truth in Firmware (`bench/autonomous_tuning.c` & flash records)**:
- `case_00` to `case_03` are Axis 0 (EV3 Large)
- `case_04` to `case_07` are Axis 1 (EV3 Large)
- `case_08` to `case_11` are Axis 2 (EV3 Medium)
- `case_12` to `case_15` are Axis 3 (EV3 Medium)

Therefore:
- `case_12` is actually **Axis 3 (EV3 Medium)** NEG repeat 0.
- `case_15` is actually **Axis 3 (EV3 Medium)** POS repeat 3.
- `case_09` is actually **Axis 2 (EV3 Medium)** POS repeat 1.
The prior agent completely misattributed which motors and axes were achieving passing scores, creating false conclusions about EV3 Large stability versus EV3 Medium stability.
