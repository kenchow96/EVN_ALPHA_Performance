# EVN ALPHA Performance — Comprehensive Audit Report
**Date**: 2026-09-09

## Executive Summary

The EVN_ALPHA_Performance project suffers from significant technical debt and process degradation due to extended agentic development without regular consolidation. Critical issues include:

1. **Firmware defaults mismatch**: Current `motion/motion_engine.c` defaults do NOT match documented winning configurations from autonomous runs, invalidating performance claims.
2. **Blocking delays in real-time paths**: Multiple `busy_wait_ms/us` calls violate AGENTS.md Rule #1 (no blocking delays).
3. **I2C firmware race**: `hal_battery_service()` corrupts user-initiated I2C scans by calling `hal_i2c_select_port(16)` mid-scan.
4. **Documentation scatter & staleness**: Duplicated sections in ASSUMPTIONS.md, stale Status Board, broken references, inconsistent phase numbering.
5. **Repository pollution**: ~268 untracked `test_*.txt` and `validation_*.txt` files in repo root from tooling CWD-relative outputs.
6. **Tooling duplication**: Multiple copies of port/BOOTSEL detection logic, dead/legacy scripts, dashboard thread-safety gaps.
7. **Process breakdown**: Session index (`docs/resume/index.md`) is 3+ sessions stale, violating its own canonical entry point protocol.

Without fixing the stale firmware defaults, all claims of antibiotic performance breakthroughs are invalid — the flashed firmware runs outdated parameters.

## Detailed Findings

### 1. Firmware Core Layer
**Critical:** Gain mismatches and blocking delays violate core assumptions.

- **Gain inconsistency** (`motion/motion_engine.c` lines 111-130):
  - EV3 Large defaults: `kp_pos=4.0e-4f, kp_vel=5.0e-6f, endpoint_kp_vel=1.0e-6f` (matches documented)
  - EV3 Medium defaults: `kp_pos=2.5e-4f, kp_vel=1.0e-6f, ki_pos=8e-7f, kd_vel=0f, endpoint_kp_vel=2.0e-6f, start_duty=0.80f, accel_scale=0.35f` (matches documented)  
  - **BUT** `bench/autonomous_tuning.c s_cases[]` uses different gains for EV3 Large cases (e.g. `kp=2.0e-4f, kp_vel=1.0e-5f` in latest runs) — creating ambiguity between validated defaults and tuning harness.
- **Blocking delays violating AGENTS.md** (no sleep_ms/sleep_us):
  - `EVN_ALPHA_Performance.c:569`: `busy_wait_ms(100)` before reboot (USB re-enumeration)
  - `EVN_ALPHA_Performance.c:609`: `busy_wait_ms(80)` in startup LED blink
  - `EVN_ALPHA_Performance.c:657`: `busy_wait_ms(100)` in idle timeout handler
  - `hal/hal_i2c.c:208-216`: Multiple `busy_wait_us(5)` in I2C stuck-bus recovery (per AUDIT_REPORT.md)
- **HAL violation**: `motion/core1.c:80` direct timer register access (`hw_set_bits(&timer_hw->inte, alarm_mask)`) bypasses HAL layer.
- **Run ID staleness**: `hal/hal_tuning_log.h:18` shows `EVN_TUNING_RUN_ID 0x2609044Du` (2026-09-04 run #43) but git log shows runs through 0x2609044E already completed — index.md still claims next run is 0x26090449.

### 2. HAL Layer
**Critical:** I2C race condition and API gaps.

- **I2C firmware race** (Docs/PROCEDURES.md issue #3/#4): 
  - `hal/hal_battery.c:93` calls `hal_i2c_select_port(BQ_PORT)` every 20ms in `hal_battery_service()`
  - No scan-active guard exists — user I2C scans get corrupted when battery service fires mid-scan.
- **Missing declarations** (potential link errors):
  - `hal_button_set_callback()` used in `EVN_ALPHA_Performance.c` but not declared in `hal_button.h` (per earlier audit).
  - `hal_battery_debug_regs()` and `hal_i2c_cached_channel()` referenced but may lack prototypes.
- **API consistency**: Generally good — all HAL .h/.c pairs match; no unused functions detected.
- **Non-blocking design**: Battery service uses timed state machine (`s_adc_due_us = now + BQ_ADC_SETTLE_US`) — no blocking delays.

### 3. Tooling & Scripts
**Critical:** Root pollution and duplication undermine agentic reliability.

- **Root pollution source**: 
  - `tools/run_validation.py` and similar scripts write `test_*.txt` and `validation_*.txt` files to CWD (repo root) via relative paths like `f"test_axis{axis}_{repeat}.txt"`.
  - **Count**: 252 `test_*.txt` + 16 `validation_*.txt` = 268 untracked polluting repo root (per `git status --short`).
- **Duplication**:
  - **COM-port auto-detection**: 5+ copies across `serial_capture.py`, `flash_and_capture.py`, `flash_extract_decode.py`, `evn_dashboard.py`, `_common.py`.
  - **BOOTSEL detection/waiting**: Copies in `check_bootsel.ps1`, `wait_bootsel.ps1`, plus logic in `flash_extract_decode.py` and `evn_dashboard.py`.
  - **Serial capture logic**: Redundant implementations in `serial_capture.py`, `flash_and_capture.py`, `flash_extract_decode.py`.
- **Dead/legacy code**:
  - `tools/legacy/` contains `motion_sweep.py`, `tune_cmd.py`, `tune_session.py`, `analyze_trace.py`, `batch_sweep.py`, `sysid_motor.py`, `local_commit_bot.py` — none imported by live scripts but clutter namespace.
  - Superseded top-level scripts: `motion_metrics.py` (partially duplicated by newer tools).
- **Dashboard (`evn_dashboard.py`) remaining issues** (per PROCEDURES.md audit):
  1. **tk.Canvas recoloring**: Motors/Servos tab canvases not updated in `toggle_dark_mode()`.
  2. **Servo pulse label**: Unverified if port-number display persists.
  3-4. **I2C scan firmware race**: Dashboard-side fix impossible — requires firmware guard (see HAL findings).
  5. **CDC port detection**: `_find_cdc_port()` still uses substring matching (`'Pico'/'USB'/'Serial'`) instead of `port.vid == 0x2E8A`; `_attempt_reconnect` may not reschedule on failure.
- **flash_extract_decode.py**: Prior audit noted summary-table column bug — current status unknown but critical for autonomous validation integrity.
- **`_common.py`**: Exists but underused — many scripts duplicate its intended utilities (port detection, trace parsing).
